# 대형 편대 성능 확인 — 2026-09-30

## 원인

실제 서울 서버에서 AI 한 편대가 드론 430기를 보유한 전장을 캡처했다. 전체 드론은 696기(회색 드론 231기 포함)였다. 10초 동안 받은 시뮬레이션 프레임은 156개였고 입력 프레임의 JSON 크기는 약 12 KB였다. 이 측정에서는 대역폭보다 시뮬레이션 계산이 병목이었다.

서버는 60 Hz로 전장 전체를 계산하고 입력 프레임을 보낸다. 브라우저도 같은 전장을 계산한다. 전체 위치 정보는 입장·퇴장·재동기화 스냅샷에 포함되고, 일반 프레임마다 모든 드론 위치를 보내지는 않는다. 화면 밖의 드론도 다른 편대에 영향을 주므로 계산에서 제거할 수 없다.

## 변경

- 공간 격자의 조회에서 문자열 키 생성 대신 숫자 행·열 조회를 사용한다. 후보 방문 순서는 유지한다.
- 적 편대의 영향 범위와 겹치지 않으면 영향력 검사를 건너뛴다.
- 정지한 회색 드론은 합류·유예 시간 계산만 수행하고 불필요한 이웃 비행 계산을 생략한다.
- 분리 힘, 상류 이웃, 최근접 7기 선택 어디에도 영향을 줄 수 없는 후보는 비싼 거리 계산 전에 제외한다. 근접 경계와 동률은 기존 계산을 사용한다.
- 클라이언트가 패킷을 기다린 시간을 누적해, 다음 3틱을 한 번에 처리하던 현상을 수정한다. 실제 밀린 프레임의 제한된 따라잡기는 유지한다.

편대 상한, 성장, 이동·충돌 규칙과 난수 순서는 바꾸지 않았다.

## 검증

- 같은 실제 전장 복사본의 300틱 계산: 로컬 Node.js 24에서 평균 22.40 ms → 8.44 ms/틱. 약 62% 감소, 약 2.65배 처리 속도. 서버나 모든 기기의 FPS 보장 수치가 아니다.
- 수정 전후 같은 전장을 2,400틱 실행해 120틱마다 비교한 정확한 상태 지문 20개가 모두 일치했다.
- 전체 자동 테스트 413개 통과. 격자 방문 순서·경계·동률, 회색 드론 합류, 패킷 대기 후 프레임 진행 검사를 포함한다.
- 실제 SDK 두 연결에서 430기 이상 AI 편대의 상태 지문이 일치했다. 두 복제 시뮬레이션을 같은 Node 프로세스에서 실행하면 검사기 자체도 CPU를 사용하므로 이 결과를 서로 다른 기기의 FPS로 해석하지 않는다.
- 별도 단일 클라이언트 검사에서 최대 편대 491기, 전체 791기 상태를 10초 동안 평균 59.8틱/초로 진행했고 상태 지문 10개가 일치했다. 이는 로컬 테스트 서버 측정이다.

극단적으로 밀집시킨 추가 검사에서는 860기 편대가 약 31 ms/틱, 1,290기가 약 60 ms/틱이었다. 무제한 성장 규칙은 유지했지만 처리 가능한 개체 수가 무한한 것은 아니다. 이후에도 대형 편대에서 문제가 남으면 이 전장 크기를 기준으로 추가 최적화해야 한다. 접속자 수만 늘리는 검사는 장시간 성장에 따른 성능을 검증하지 못한다.

## 첫 입장 끊김 추가 수정

첫 입장 때 서버가 자동으로 보내는 전장 스냅샷과 클라이언트의 즉시 재동기화 요청이 겹쳐, 브라우저에서 스냅샷을 두 번 복원하는 것을 확인했다. 첫 포인터 입력은 음원 69개(약 5 MB)의 다운로드·디코딩도 한꺼번에 시작했고, 연결용 모듈은 입장 버튼을 누른 뒤에야 가져왔다.

- 정상 입장에서는 환영 메시지와 스냅샷을 기다린다. 둘 중 하나가 오지 않으면 1.8초 뒤 기존 재동기화 경로로 복구한다. SDK가 등록 즉시 메시지를 재전달하는 경우와 연결 취소도 처리한다.
- SDK와 프로토콜 모듈은 시작 화면의 첫 프레임 이후 미리 불러온다. 실제 방 접속과 설정 확인은 입장 시 수행한다.
- 음원 다운로드·디코딩은 다음 작업으로 미루고 동시 두 개로 제한한다. 현재 필요한 음악과 효과음을 우선하며, 늦게 도착한 일회성 효과음을 뒤늦게 재생하지 않는다.
- 클라이언트의 프레임 따라잡기는 약 8 ms를 기준으로 나눈다. 30 Hz 화면에서도 서버의 60 Hz 진행을 따라갈 수 있도록 실제 밀린 계산이 있으면 두 번째 틱까지 허용한다. 틱 중간을 끊거나 생략하지 않는다. 한 틱 자체의 비용이 큰 경우 8 ms를 넘을 수 있다.
- 전장 입장 UI와 HUD 초기화를 매 시뮬레이션 갱신마다 반복하지 않는다.

로컬 Chrome에서 같은 대형 전장 캡처로 시작한 서버에 입장해 측정했다. 수정 전 첫 6초에는 스냅샷 복원 2회, 25 ms 초과 계산 갱신 11회(최대 48 ms), 30 ms 초과 화면 간격 8회였다. 최종 수정본에서는 복원 1회, 25 ms 초과 계산 갱신 2회(최대 29.8 ms), 30 ms 초과 화면 간격 3회였다. 두 실행 사이 전장은 계속 진행하므로 위치와 성장 상태가 완전히 같은 엄밀한 속도 비교는 아니다. 첫 클릭·모듈 로딩 지연은 캐시와 네트워크 조건의 영향도 받는다.

최종 브라우저 실행에서 AI 최대 편대는 430~437기였고, 첫 20초 동안 처리 대기 프레임은 최대 4개, 마지막에는 0개였다. 음원 동시 작업 최대 2개와 콘솔 오류 없음도 확인했다. 전체 자동 테스트 420개와 멀티플레이 빌드가 통과했다. 첫 입장 개선이며, 매우 큰 편대의 개별 틱 비용 자체를 없애는 변경은 아니다.

## 계산 결과를 유지하는 CPU 최적화

전장 전체를 서버와 클라이언트가 각각 계산하는 기존 구조를 유지하면서 반복 연산과 임시 할당을 줄였다. 60 Hz, 게임 규칙, 난수 순서, 이웃 탐색·동률 처리·정렬 순서, 상태 형식과 통신 프로토콜은 유지한다.

- 편대의 공통 계수, 지휘기의 속도·방향, 모이기 반응 계수를 드론마다 다시 계산하지 않고 한 편대 갱신 동안 재사용한다. 부동소수점 연산의 피연산자와 결합 순서는 유지한다.
- 드론 조종 계산에 이미 구한 흐름 속도·순항 속도·연결 거리를 전달한다. 직접 호출하는 기존 경로도 유지한다. 재사용 데이터는 해당 편대 갱신이 끝나면 무효화하며, 상태 저장 대상에 넣지 않는다.
- 이전 드리프트 값을 읽기 위한 Map과 레코드를 재사용한다. 매 갱신의 시작 값으로 다시 채우고 종료 시 참조를 비운다.
- 결정론 수학의 두 숫자 거리 계산은 가변 인자 순회 대신 같은 순서의 스칼라 계산을 사용한다. 기존 제곱근, 범위 정규화, 양의 0부터 시작하는 합산, Infinity·NaN 처리를 유지한다. 다른 인자 형식은 기존 경로를 사용한다.

같은 696기 전장 복사본을 매번 복원하고 120틱 준비 후 600틱을 측정했다. 수정 전·후 실행 순서를 번갈아 바꾼 4쌍의 로컬 Node.js 24 측정에서 평균 **8.776 → 7.888 ms/틱**, 약 **10.1% 감소**였다. 각 측정 쌍에서 감소했고 최종 상태 지문은 모두 같았다. 화면 그리기·네트워크를 포함한 FPS 측정이나 운영 서버의 개선율은 아니다.

검증:

- 수정 전 원본과 수정 후를 각각 6,300틱 진행했다. 전체 상태 115개 비교 지점과 생성·재출격 식별자 60개 비교가 모두 정확히 일치했다. 실제 대형 전장, 860기 밀집 편대, 2·8·30명 입력, 퇴장·재입장, 사망·재출격, 중간 저장·복원, 일반 편대전 세 시드를 포함한다.
- 최적화된 로컬 서버에 수정 전·후 SDK 클라이언트를 별도 프로세스로 동시에 연결했다. 약 15초에 각각 902·903틱을 처리했고, 서버 지문 15회가 양쪽 모두 일치했다. 최대 편대 431기, 전체 686기였으며 상태 불일치 오류는 없었다. 초기 입장과 명시적 초기 동기화에 따른 스냅샷은 포함한다.
- Node.js 24.21.0, Chrome 154, macOS JavaScriptCore에서 같은 원본·수정본 비교 묶음을 실행했다. 430·860기 편대를 각각 360틱 진행하고 중간 복원을 거쳤으며, 환경별 전체 상태 비교 12개 지점이 모두 일치했다. 각 환경의 7,328,558바이트 상태 결과 SHA-256도 `a488fcd004410395ff710d8c21127b26b1dafd614bb1bee014255c4fef91d4da`로 동일했다. JavaScriptCore는 시스템 엔진 실행이며 Safari 전체 브라우저 검사는 아니다.
- 거리 계산의 20,000개 입력과 극단값·인자 수·형식 비교, 편대 간 재사용 데이터 격리와 상태 복원 검사를 추가했다. 전체 자동 테스트 **423개 통과**, 멀티플레이 빌드 성공.

이웃 후보를 여러 틱 재사용하거나 검사 순서를 바꾸는 변경은 이번 최적화에 포함하지 않았다. 그런 변경은 별도로 후보 누락과 누적합 순서의 동등성을 입증해야 한다.

## 주기적 동기화 확인의 중복 변환 제거

이후 재측정에서 매 60틱의 상태 지문 확인에도 한 번에 약 6~11 ms가 필요했다. 라이브 상태를 복사하면서 `encode → decode → 검증 → encode`를 거치던 경로에서 처음 두 변환을 하나로 합쳤다. 전체 데이터 복사 한 번과 키 정렬 한 번을 제거하고, 오류 경로 문자열은 실패할 때만 만든다. 정상 여부 검증, 독립된 복사본 반환, 특수 Float64 태그 정규화, JSON 키·개체 순서와 기존 지문 계산은 유지한다. 계산 주기·전송 주기·게임 규칙은 변경하지 않는다.

이전 CPU 최적화가 적용된 696기 전장을 기준으로 수정 전후를 번갈아 4쌍 측정했다. 라이브 상태 복사·지문을 30회 준비하고 각 경로를 쌍마다 80회 측정한 로컬 Node.js 결과다.

| 작업 | 수정 전 평균 | 수정 후 평균 | 감소 |
| --- | ---: | ---: | ---: |
| 라이브 전장 동기화 지문 | 6.424 ms | 4.501 ms | 29.9% |
| 라이브 전장 상태 복사 | 4.306 ms | 2.341 ms | 45.6% |
| 이미 저장된 상태의 지문 | 4.676 ms | 4.169 ms | 10.8% |

모든 측정 쌍에서 비용이 줄고 지문이 같았다. 이는 주기적 상태 처리의 측정값이며, 전체 게임 CPU 또는 화면 FPS 개선율이 아니다. 편대 이웃 탐색이 여전히 매 틱 계산의 주된 비용이다.

- 독립적으로 보관한 수정 전 코드와 2,280틱 진행 및 특수값·순서·변경 입력을 포함한 전체 상태 66개를 비교했다. JSON 바이트와 지문이 모두 같았다. 잘못된 라이브 상태 25종을 동일하게 거부했고, 잘못된 복원 9종에서 기존 게임·난수 상태가 유지됐다.
- Node.js, Chrome, macOS JavaScriptCore에서 정상 변형 6종과 오류 6종을 각각 비교했다. 2,780,049바이트 결과의 SHA-256은 세 환경 모두 `231015460547103d3d0435bc492ae060488420c73dff861d970b447a6a48426c`였다. JavaScriptCore는 엔진 검사이며 Safari UI 검사가 아니다.
- 수정 전·후 SDK 클라이언트를 별도 프로세스로 로컬 서버에 함께 연결했다. 약 15초 동안 각각 903·900틱, 공통 서버 지문 15개가 모두 일치했고 상태 불일치 오류가 없었다. 최대 편대 431기, 전체 686기였다.
- 관련 검사 17개, 전체 자동 테스트 **437개 통과**, 멀티플레이 빌드 성공. 이 작업은 소스 반영과 로컬 검증이며 운영 배포는 하지 않았다.
