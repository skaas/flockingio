# 편대전 결정론 리뷰

2026-09-30 · 코드 검토와 실행 비교 · 게임 소스 변경 없음

## 판단

결정론을 활용하는 멀티플레이로 발전시킬 수 있다. 시드 난수, 고정 60Hz, 입력 기반 재생, 화면과 시뮬레이션의 분리는 이미 구현되어 있다. 기존 작업은 실제로 같은 환경에서 재현 가능한 시뮬레이션을 만들었다.

현재 확인한 수준은 **같은 실행 환경과 같은 처리 순서에서의 재현성**이다. Node와 브라우저가 입력만 교환하고 장시간 상태 보정 없이 완전히 같은 전투를 계산하는 엄격한 결정론은 아직 보장하지 않는다. 아래 항목을 보강하면 기존 엔진을 활용할 수 있다.

일반 편대전 시드는 1, 7, 11, 23, 41, 99, 12345, 4294967295였으며 각각 종료 또는 7,200단계까지 비교했다. 추가 세 시나리오는 플레이어의 초기 편대를 4/32/128기로 설정해 1,800단계를 비교했다. 이 세 시나리오에서는 상대 편대 생성을 막았고 현재 게임의 주변 중립 드론 공급·합류는 유지했다.

같은 환경의 비교는 주요 게임 스칼라, 지휘기·드론의 스칼라, 난수 상태, 편대·중립 드론 배열, 소속 변경 대기열을 직렬화해 비교했다. 숫자는 Float64 비트 표현으로 비교했다. 렌더링 캐시와 모든 중첩 객체를 포함한 완전한 저장·복원 검증은 아니다. 서로 다른 엔진 비교는 같은 소스 묶음을 사용했으며, Node의 원본 모듈 실행과 묶음 실행도 해당 시드에서 일치했다.

## 확인 사항과 보완점

### 1. 실행 환경별 수학 함수 차이 — 엄격한 입력 동기화의 우선 과제

관련: `src/engine.mjs:13`, `src/engine.mjs:211`, `src/engine.mjs:810` 부근과 편대전의 공통 수학 연산.

시드와 코드가 같아도 초기 드론 속도부터 차이가 재현된다. 예를 들어 Node와 JavaScriptCore에서 같은 드론의 `vy`가 각각 `-50.82152700448055`, `-50.821527004480544`였다. 난수 순서가 달라진 것이 아니라 같은 입력으로 계산한 수치가 끝자리에서 달라졌다.

현재 코드에는 `sin`, `cos`, `atan2`, `hypot`, `exp`, 비정수 거듭제곱 등이 사용된다. 삼각함수를 포함한 일부 JavaScript 수학 함수에는 구현별 근사 차이가 허용된다. 참고: [ECMAScript Math.sin](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-math.sin).

이 실험의 30초 구간에서는 격추·생존 상태·드론 수가 달라지지 않았다. 따라서 실제 전투 결과가 곧바로 어긋난다고 주장할 근거는 없다. 다만 보정 없는 입력 동기화에 필요한 비트 단위 일치는 이미 실패한다.

권장: 시뮬레이션 수학 계층을 공통화하고, 고정소수점/정수 기반 계산과 결정론적인 근사·룩업 함수 등으로 중요한 연산의 결과를 규정한다. 단순히 전송 좌표를 반올림하거나 WebAssembly로 옮기는 것만으로 보장된다고 가정하지 않는다. 변경 후 조종 감각과 충돌 경계도 재검증한다. 주기적인 서버 보정을 허용하는 방식이라면 요구 수준을 달리 잡을 수 있다.

### 2. 드리프트가 배열 순서에 의존 — 순서 보존과 이전 상태 읽기 필요

관련: `src/fleet-battle.mjs:87–95`, `src/engine.mjs:659–662`.

속도와 위치는 계산 후 일괄 반영하지만, 드리프트는 각 드론을 처리하는 도중 `b.drift`에 바로 반영한다. 뒤에서 처리되는 드론은 `flow.drift`를 통해 앞 드론의 이번 단계 값을 읽을 수 있다. 배열 순서를 바꾸면 전달 속도가 달라진다.

중립 공급과 적 생성을 끈 64기 장면에서, 초기 위치·속도·입력을 유지하고 한쪽 드론 배열만 뒤집었다. 5초 이내 최대 위치 차이는 약 11.15였다. 임시 실험에서 앞 드론의 이전 드리프트를 읽게 하자 차이가 약 9.17e-13으로 줄었다. 실험용 일관된 정렬을 적용하면 차이가 0이었다.

이것은 같은 배열 순서로 반복 실행했을 때 결과가 무작위라는 뜻은 아니다. 현재 **배열 순서도 시뮬레이션 상태의 일부**다. 네트워크에서 상태를 복원하거나 참가자별로 배열을 재구성할 때 그 순서가 달라지면 안 된다.

권장: 드론에 안정적인 고유 ID를 부여하고 생성·순회·동률 우선순위·합류 순서를 고정한다. 드리프트도 이전 값과 다음 값을 분리한다. 이전 값 분리만으로 합산 순서에 따른 극미세한 부동소수점 차이까지 없어진 것은 아니므로 정렬 규약도 필요하다. 실험에서 정렬 키로 쓴 난수 `seed`는 제품용 고유 ID의 대체물이 아니다.

### 3. 현재 재생 지문은 핵심 상태 차이를 놓침

관련: `src/replay.mjs:22–33`.

현재 지문은 수치를 0.001 단위로 반올림하고 일부 필드만 포함한다. `turnRate`, `gather`, `drift`, `driftOwner`, `influenceTarget`, `hovering`, 개체별 특성, AI 제어 상태, 편대 증원·중립 드론 보충 상태 등 다음 계산에 영향을 주는 값이 충분히 포함되지 않는다.

실험에서 지휘기 `turnRate`, 드론 `gather`, `fleetSpawnAt`을 각각 바꾸어도 변경 직후 지문은 같았다. 이미 초기화된 드론의 드리프트만 0.9로 바꾼 실험도 지문은 같았고, 다음 한 단계의 위치가 약 0.00455만큼 달라졌다. 아주 작은 좌표 차이 역시 반올림 때문에 숨겨졌다.

권장: 다음 계산에 필요한 상태를 명시적으로 정의하고 그것을 해시·저장·복원에서 함께 사용한다. 정수화된 상태라면 정확한 정수 값을, 부동소수점 상태라면 진단용으로 Float64 표현을 비교한다. 32비트 해시 일치만으로 상태 동일성을 증명하지 말고 디버그 시 최초로 다른 필드를 출력한다.

### 4. 시각 효과가 전투 난수와 같은 흐름을 사용함

관련: `src/engine.mjs:298–301`.

`burst()`가 파티클을 생성할 때 전투용 `this.random`을 소비한다. 현재 모든 실행이 같은 효과 함수를 호출하면 결정론은 유지된다. 다만 서버로 옮기면서 파티클 생성을 생략하거나 클라이언트 품질 옵션에 따라 생략하면 이후 전투 난수 순서가 달라진다.

같은 적 격추를 두 번 계산하되 한쪽의 파티클만 생략한 실험에서 처치 수는 둘 다 1이었으나 난수 상태가 `3472798599`와 `1266743693`으로 달라졌고, 다음에 생성한 편대의 첫 드론 위치도 달랐다.

권장: 전투 RNG와 효과 RNG를 분리하거나, 효과를 결정론적 전투 이벤트로부터 브라우저에서 생성한다. 난수 소비 규칙이 달라지는 변경이므로 재생 규칙 버전도 관리한다.

### 5. 현재 편대전에는 재생·복원 연결 작업이 남아 있음

관련: `src/app.mjs:349–360`, `src/replay.mjs:91–100`.

현재 앱은 편대전 입력을 기록하지 않으며, `validReplay()`는 `fleet-battle` 모드를 허용하지 않는다. 기존 모드의 16기 최대 편대 검증도 남아 있다. 실제 편대전 입력을 임시 기록한 결과는 `validReplay()`에서 거부되었다.

이는 현재 편대전에서 옛 재생 화면을 제거한 제품 설계와 일치한다. 기존 싱글플레이 버그로 분류할 사안은 아니지만, 결정론 네트워크 검증에는 편대전용 입력 기록과 전체 상태 저장·복원 경로를 추가해야 한다.

## 이미 마련된 기반

- `seededRandom()`은 명시적 32비트 난수 상태를 제공한다. 시작 시 앱이 새 시드를 설정한 후 전장을 초기화한다.
- 앱의 고정 60Hz 계산과 시뮬레이션 내부의 `elapsed`를 사용한다. 전투 엔진에서 벽시계·네트워크 응답을 읽는 경로는 발견하지 못했다.
- 순수 게임 계산을 Node에서 실행할 수 있다. 브라우저 이벤트는 계산에 앞서 입력으로 변환된다.
- 대부분의 이동 계산은 기존 상태를 읽고 다음 값을 일괄 적용한다.
- 충돌·주변 이웃 검사는 공간 격자를 활용한다.
- 공통 규칙 버전과 기존 시드·입력 기반 재생 검증이 있다.

## 권장 작업 순서

1. 시드·규칙 버전·정수 틱·참가자 입력을 받는 공통 시작/진행 경로와 상태 명세를 만든다. 현재 앱과 테스트의 시드 설정 시점 차이를 한 진입점으로 정리한다.
2. 전투/효과 RNG를 분리하고 드론 고유 ID·순회 순서·동률 처리 규칙을 고정한다. 드리프트를 이전/다음 상태로 분리한다.
3. 엄격한 결정론을 목표로 하는 수학 계층을 구현하고, 동일 입력 자료로 Node·Chromium·JavaScriptCore를 비교한다. 현행 부동소수점+주기 보정을 택할 경우 허용 오차와 보정 규칙을 별도로 정한다.
4. 편대전 입력 기록, 완전한 상태 해시, 중간 상태 저장/복원과 중간 참가 재현을 연결한다. 난수 상태뿐 아니라 AI 타이머, 보충 일정·위상, 소속 변경 대기열, 드론 속성도 보존한다.
5. 서버가 입력 적용 틱과 늦은 입력 처리 규칙을 확정하는 최소 2인 전장으로 검증한다. 30명 전체 입력을 매번 무기한 기다리는 정책은 피하고 예측·확정 입력·재계산 정책을 설계한다.

서버가 기준 시뮬레이션을 실행하면서 클라이언트에 확정 입력과 필요한 복원 정보를 보내는 구성을 사용할 수 있다. 모든 드론 좌표를 매번 보내야 한다는 전제는 필요하지 않다. 결정론만으로 드론 이동·충돌 계산량까지 사라지는 것은 아니다.
